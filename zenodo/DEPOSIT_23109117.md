# TWO FIELDS THE API SILENTLY DISCARDS — add them in the web UI

Zenodo's **deposition** endpoint accepts `subjects` and `references` without
error and then does not persist them. It echoes neither back on read. This is
worth stating plainly: the upload reports success, the verification read shows
zero, and nothing anywhere warns you. Both fields were therefore verified
against the live API rather than assumed.

**Add these two fields in the Zenodo web form before publishing.**

# DEFECT FOUND IN THE PUBLISHED BATTERY RECORD

While filling these fields, the published record `10.5281/zenodo.23101903` was
inspected and **its `references` field is corrupt**.

```
expected : 4 citations
actual   : 722 array entries, each a SINGLE CHARACTER
          ["B", "u", "t", "l", "i", "n", ",", "P", ".", ...]
```

Cause: the local `zenodo/metadata.json` stored `references` as one concatenated
**string**. The upload passed it through, and Zenodo iterated the string into
characters. Nothing warned, because a 722-element array of one-character strings
is valid JSON.

The four citations were not lost — they survive concatenated — and have been
recovered and written back to the battery repository as a proper list, with the
ids from the Subjects table above replacing the free-text subjects that Zenodo
discarded. A note recording both defects is in that file.

**This cannot be fixed in place.** Zenodo records are immutable. Correcting
`10.5281/zenodo.23101903` requires publishing a **new version**. Worth doing:
the references are unreadable to any consumer, and the record shows no subjects
at all.
